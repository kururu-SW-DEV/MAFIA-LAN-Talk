# v6.21 — 이모지 피커 로딩 속도 개선 + 누락 이모지 점검 (2026-09-13)

## 계기

"이모지 선택하는 탭을 보면 불러오는 속도가 느려, 빨리 불러오게 바꿔줘. 그리고,
일부는 현재 컴에 폰트가 없어 안 나오는 이모지도 있어. 확인해줘" — 두 가지 요청.

## (1) 로딩 속도 개선

- **원인 분석**: `EmojiPicker._switch_cat()`이 탭을 바꿀 때마다 카테고리 안의 이모지
  전부(스마일리는 최대 86개)를 개별 `tk.Label` 위젯으로 새로 만들고, 위젯마다
  클릭·마우스오버·마우스아웃 바인딩을 3개씩 걸고 있었다. 실측해보니 이 작업 자체는
  탭당 수십 ms 수준이라 크게 느리진 않았지만, **더 큰 병목은 Windows가 "Segoe UI
  Emoji" 컬러 폰트의 글리프 메트릭을 그 폰트로 처음 뭔가를 그릴 때 한 번 계산해두는
  비용**이었다 — 실측 결과 그 카테고리를 맨 처음 그릴 때만 카테고리당 300~1000ms가
  걸리고, 이후로는 같은 카테고리든 다른 카테고리든 전부 10ms 안팎으로 빨라졌다.
  즉 사용자가 "느리다"고 느낀 건 이 앱을 켜고 이모지 버튼을 맨 처음 눌렀을 때(또는
  아직 한 번도 열어보지 않은 카테고리로 처음 넘어갈 때) 매번 이 비용을 새로 치르고
  있었기 때문이다.
- **수정 1 — 위젯 생성 자체도 가볍게**: 이모지 그리드를 `tk.Label` N개 대신, 하나의
  `Canvas`에 `create_text`로 직접 그리고 클릭/호버는 위젯 하나하나가 아니라 태그
  하나(`"emoji_item"`)에 `tag_bind`로 한 번만 건다(`Canvas.find_withtag("current")`로
  지금 클릭/호버된 항목을 알아낸다). 위젯 인스턴스화 비용과 바인딩 개수를 최대
  86개+258바인딩 → 1개 캔버스+3바인딩 수준으로 줄였다(스티커 탭은 항목이 28개뿐이라
  원래도 체감상 문제없어 그대로 뒀다).
- **수정 2 — 폰트 예열(prewarm)**: 어차피 첫 렌더 비용 자체는 없앨 수 없으니(Windows/
  Tk 쪽 비용), 그 비용을 **사용자가 실제로 버튼을 누르기 전, 창이 뜨고 0.3초 뒤에
  백그라운드로 미리 치르도록** `app.py`에 `_prewarm_emoji_fonts()`를 추가했다 —
  이모지 피커의 모든 카테고리를 한 번씩 `_switch_cat()`으로 조용히 그려본 뒤 원래
  탭으로 되돌린다. 피커 자체는 아직 화면에 붙어있지 않은(pack 되지 않은) 상태라
  아무 것도 깜빡이지 않는다.
- **부수적으로 발견한 버그**: 캔버스 방식으로 바꾸는 과정에서 `self._emoji_map`
  (캔버스 아이템 id → 이모지 문자 매핑)을 탭을 바꿀 때마다 지우지 않고 계속
  누적시키고 있어서, 오래 쓰면 이미 삭제된 캔버스 아이템 id가 매핑에 계속 쌓이는
  문제를 검증 중 발견해 `_switch_cat()` 맨 앞에서 `self._emoji_map.clear()`를
  추가해 고쳤다.
- **검증**: 실제 `App`을 띄워 (1) prewarm 없이 첫 렌더가 실제로 300~1000ms대로
  느린 것부터 재현 확인, (2) 같은 카테고리를 두 번째부터 그릴 때 10ms 안팎으로
  빨라지는 것 확인, (3) prewarm이 실행된 뒤에는 사용자가 실제로 처음 여는 순간에도
  60ms 이하로 빠른 것 확인, (4) 캔버스 클릭이 정확한 이모지로 `on_select`를 호출하는지,
  호버 시 글자색이 밝아졌다가 벗어나면 원래 카테고리 색으로 돌아오는지, (5) "최근"
  탭이 비어 있을 때는 여전히 기존 방식(Label 안내 문구)으로 잘 뜨는지까지 확인 —
  전항목 통과. 기존 회귀 스위트 3종도 재통과.

## (2) 폰트에 없어서 안 나오는 이모지 — 점검 결과

- **1차 시도(GDI `GetGlyphIndicesW`)는 오탐**: Windows GDI로 "Segoe UI Emoji" 폰트를
  선택해 코드포인트별 글리프 존재 여부를 물어봤더니, 😀·👍처럼 절대 없을 리 없는
  극히 기본적인 이모지까지 전부 "없음"으로 나왔다 — 이건 실제 결함이 아니라, 이
  폰트가 컬러 글리프를 **비트맵(CBDT/CBLC)**으로 저장하는데 레거시 GDI 텍스트
  경로가 이 포맷을 제대로 못 읽어서 생기는 오탐이라고 판단해 이 방법은 버렸다.
- **2차 시도(폰트 파일의 cmap 테이블 직접 파싱)**: `C:\Windows\Fonts\seguiemj.ttf`
  파일을 열어 cmap 서브테이블(포맷 12, 총 2028개 코드포인트 커버)을 직접 읽어
  이 프로그램이 쓰는 이모지 269개 + 탭 아이콘 전부를 대조한 결과, **이 PC의 폰트
  파일에는 전부 들어있었다**(`NO_MISSING_GLYPHS_FOUND`).
- **3차 시도(실제 Tkinter 렌더 폭 측정)**: 폰트 파일에 있어도 Tk가 실제로 못 그릴
  가능성까지 감안해, 앱과 똑같은 방식(`Canvas.create_text`, `("Segoe UI Emoji", 14)`)
  으로 269개 전부를 직접 그려보고 렌더된 폭을 쟀다. 정상 이모지 기준폭(😀 기준
  32px)과 비교했을 때 전부 31~32px로 균일하게 나와, **이 PC에서는 렌더 실패(빈
  네모/미표시)로 의심되는 문자가 하나도 없었다**.
- **결론**: 지금 이 PC(개발/검증에 쓰인 PC)에서는 폰트 파일과 실제 렌더링 둘 다
  문제가 없다는 게 확인됐다. 사용자가 신고한 "일부 안 보이는 이모지"는 **이
  프로그램을 켜서 대화하는 다른 PC**(사내망의 다른 동료 컴퓨터, 또는 이 프로그램
  자체는 P2P라 PC마다 Windows 버전·업데이트 상태가 다를 수 있음) 쪽 문제일
  가능성이 높다 — 오래된 Windows 10 빌드는 Windows Update가 최신이 아니면
  `seguiemj.ttf` 자체가 구버전이라 비교적 최근에 추가된 이모지(예: 🥸 위장 얼굴
  [2020년 추가], 🤎 갈색 하트[2019년 추가] 등)가 실제로 빠져 있을 수 있다. 어느
  PC에서 어떤 이모지가 안 보이는지 스크린샷으로 확인되면 그 문자들만 교체하거나
  빼는 식으로 정확히 대응할 수 있다.
