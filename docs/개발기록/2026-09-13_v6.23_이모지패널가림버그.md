# v6.23 — 이모지 패널 "안 보임" 버그 2건 실측 수정 (2026-09-13)

## 계기

작업 파일을 다른 경로로 옮긴 뒤 사용자가 두 가지를 신고했다: "최근 사용한 이모지나
스티커가 잘 안보여", "스티커 사용 후 이모지 선택시 이모지가 안보여". 이전 세션들은
`tk.Toplevel`을 실제로 `deiconify()`하면 자동화 세션이 멈추는 환경 한계 때문에 내부
로직만 검증하고 실제 화면 캡처는 최소화해왔는데, 이번엔 사용자가 명시적으로 "스샷을
찍고 직접 조작해 가며 확인"을 요청해 실제 `App`을 화면에 띄우고 클릭·스크린샷으로
재현했다(이 세션에서는 일반 `tk.Tk()` 루트 창을 보이는 채로 여는 것 자체는 멈추지
않아 안전하게 가능했다).

## 원인 1 — 이모지 카테고리 탭으로 넘어가면 방금 전 탭(스티커/최근-없음)의 잔상이
캔버스를 덮어버림

`EmojiPicker`의 그리드 영역은 `canvas.create_window(...)`로 얹은 `self.inner`
Frame(스티커 그리드나 "최근 사용한 이모지가 없습니다" 안내문이 여기 들어감) 하나와,
이모지 카테고리는 `canvas.create_text(...)`로 캔버스에 직접 그리는 방식(v6.21 성능
개선) 두 가지가 한 캔버스를 같이 쓰고 있었다.

`_switch_cat()`은 탭을 바꿀 때 `self.inner`의 자식 위젯들을 `destroy()`하지만,
**`create_window`로 얹은 창(=`self.inner`) 자체의 크기는 자식이 없어져도 곧바로
줄어들지 않는다.** 그런데 Tk 캔버스에서 `create_window`로 만든 "진짜 자식 창"은
태그 순서(`tag_raise`/`tag_lower`)와 무관하게 **항상 다른 모든 캔버스 아이템보다
위에 그려진다**(Tk의 근본적인 레이어 제약 — 네이티브 창은 소프트웨어로 그리는
캔버스 비트맵 위에 얹히는 별도의 실제 창이라 순서를 뒤집을 수 없다). 배경색이
캔버스와 똑같아 눈에는 안 띄지만, 스티커 그리드였을 때의 큰 크기(예: 560×320)를
그대로 유지한 채 이모지 텍스트 아이템들 바로 위에 얹혀 있어 새로 그린 이모지가
전부 가려졌다 — 데이터(좌표·색·폰트)는 전부 정확했는데 화면에만 안 보이는,
스크린샷 없이는 "왜 안 보이지?"를 코드만 봐서는 알아내기 어려운 유형의 버그였다.

이 조건은 "최근"이나 "스티커"처럼 `self.inner`를 실제로 쓰는 탭에서 **일반 이모지
카테고리로 넘어갈 때만** 발생한다(반대 방향은 `self.inner`가 새로 그려지므로
문제없음) — 정확히 사용자가 보고한 두 증상(최근 탭에서 안 보임, 스티커 다음
이모지에서 안 보임) 둘 다와 일치한다.

**수정**: `_switch_cat()`에서 `self.inner`의 자식을 지운 직후, 캔버스
윈도우 아이템 자체를 `canvas.itemconfigure(self._inner_win, width=1, height=1)`로
먼저 눌러 두고, `self.inner`를 실제로 쓰는 "스티커"/"최근 없음" 분기에서만
`width=0, height=0`(Tk에서 0은 "자식이 요청하는 자연스러운 크기를 쓰라"는
특수값)으로 되돌리도록 했다. `create_window` 위치를 옮기거나 프레임 자체를
`configure(width=1, ...)`로 줄이는 방식은 (실측 결과) 즉시 반영되지 않았고,
**캔버스 아이템 옵션 자체**(`itemconfigure`)를 직접 제한하는 방식만 확실하게
먹혔다.

- **부수적으로 잡은 버그**: 이 수정을 처음 적용할 때 "자연스러운 크기로 복귀"를
  `itemconfigure(width="", height="")`로 짰다가 `_tkinter.TclError: bad screen
  distance ""`가 났다. Tcl 문서상 빈 문자열이 허용된다고 알려져 있는 것과 달리
  이 Tk 빌드에서는 실제로 거부됐다 — `width=0, height=0`이 맞는 값이었다. 이
  예외가 `_prewarm_emoji_fonts()`(v6.21, 창이 뜨고 0.3초 후 모든 탭을 미리
  한 번씩 그려 폰트 캐시를 데우는 백그라운드 작업)의 `try/except Exception: pass`
  안에서 조용히 삼켜지고 있었던 탓에, 프리웜 루프가 "스티커" 탭을 그리다 예외로
  중간에 멈추면서 **루프 끝의 "원래 탭으로 복귀" 코드가 실행되지 못해 항상 스티커
  탭에 멈춰있게** 되는 2차 증상까지 만들고 있었다 — 아래 원인 2와 겹쳐 보이는
  현상이었지만 별개의 버그였고, 이번 수정으로 둘 다 사라졌다.

## 원인 2 — 이모지 버튼을 처음 눌렀을 때 기본으로 "스티커" 탭이 열림

`EmojiPicker.__init__`은 `self._cur_cat = 1 if get_recent else 0`으로 초기
탭을 정했다. 이건 v6.16 시점(스티커 탭이 없던 때) 기준으로 "최근 탭(0번)은 첫
실행엔 항상 비어 있으니, 그다음(1번) 실제 이모지 카테고리로 바로 열자"는
의도였다. 그런데 v6.17에서 "스티커" 탭을 "최근" 바로 다음(1번)에 끼워 넣으면서
목록 순서가 `[최근(0), 스티커(1), 스마일리(2), ...]`로 바뀌었는데, 이 고정값
`1`은 그대로 남아 있어 **의도와 다르게 스티커 탭을 기본으로 열게 되는 회귀**가
생겼다. 사용자가 이모지 버튼을 눌렀을 때 "최근"은커녕 이모지 자체를 보려면
매번 스마일리 탭을 다시 눌러야 했던 것.

**수정**: 고정값 대신 `(1 if get_recent else 0) + (1 if on_select_sticker
else 0)`으로 "최근"·"스티커" 탭이 실제로 몇 개 앞에 끼어 있는지 계산해, 항상
그 다음에 오는 첫 실제 이모지 카테고리를 가리키도록 했다.

## 검증

- 실제 `App`을 화면에 띄우고(withdraw 없이) 다음을 실제 클릭 이벤트로 재현·
  스크린샷 확인:
  1. 이모지 버튼 최초 클릭 → **스마일리 탭**이 기본으로 열리는지 (수정 전: 스티커)
  2. "최근" 탭 명시적 클릭 → 미리 등록해 둔 5개 이모지(🙏🎉👍❤️😀)가 실제로
     보이는지 (수정 전: 완전히 빈 화면)
  3. 스티커 탭 클릭 → 28종 정상 표시
  4. 실제 스티커 캔버스를 클릭(진짜 클릭 경로, `_pick_sticker` 경유)해 전송 →
     패널이 자동으로 닫히는지
  5. 이모지 버튼을 다시 눌러 재오픈 → 스티커 탭 콘텐츠가 다시 보이는지
  6. **스마일리 탭 클릭(사용자가 신고한 정확한 재현 경로) → 86개 이모지가
     실제로 보이는지** (수정 전: 완전히 빈 화면, 내부 데이터는 정상인데 화면만
     비어 있었음)
  7. 되돌아가기(이모지 → 스티커) → 회귀 없이 정상 표시
  - 매 단계마다 `PIL.ImageGrab`으로 실제 화면을 캡처했고, 이 세션에서 스크린샷이
    엉뚱한 창(사용자의 실제 브라우저 등)을 잘못 잡은 전례가 있어, 캡처한 이미지가
    앱 고유의 정확한 배경색(`#25272c`) 픽셀을 충분히 포함하는지 자체 검사한 뒤에만
    신뢰했다.
- 회귀 스위트 3종(`tests/test_headless.py`, `tests/smoke_gui.py`,
  `tests/test_gui_flow.py`)을 각각 2~3회 재실행, 전부 통과. 검증 중 생성된
  `tests/tmp`, `tests/smoke`, `__pycache__`는 정리했다.

## 의도적으로 하지 않은 것

- `_prewarm_emoji_fonts()`의 `except Exception: pass`를 더 엄격하게 바꾸는 것은
  이번 범위에서 뺐다 — 원인이 된 `itemconfigure` 예외 자체를 없앴으므로 당장은
  문제가 재발하지 않지만, "예외를 조용히 삼키면서 부분적으로 실행되다 만 상태"가
  또 다른 버그를 가릴 수 있다는 점은 남아 있는 위험이다. 필요하면 프리웜 루프를
  각 탭 단위로 개별 try/except하거나 실패를 로그로 남기는 방식으로 강화하는 걸
  별도로 검토할 수 있다.
