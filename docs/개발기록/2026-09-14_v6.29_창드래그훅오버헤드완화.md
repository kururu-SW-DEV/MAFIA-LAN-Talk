# v6.29 — 창 드래그 시 WH_GETMESSAGE 훅 오버헤드 완화 (2026-09-14)

## 계기

사용자 보고: "프로그램 창의 상단을 잡고 이러저리 움직여 보면 엄청 버벅이면서 움직이는데
왜그런거야?" — 마우스보다 창이 훨씬 느리게(무겁게) 따라온다는 정밀 묘사가 뒤이어 확인됨.

## 원인 규명 과정

파이썬/Tk 애플리케이션 코드 레벨에서 원인을 찾으려 다음을 순서대로 실측했다:

1. 실제 창을 SendInput으로 여러 초간 드래그하며 `<Configure>` 핸들러 실행 시간,
   3초 주기 사이드바 폴링(`_refresh_list`)·네트워크 펌프(`_pump`)와의 겹침, Tk
   이벤트 루프 틱 간격을 계측 — 전부 무시할 수준(개별 호출 0.01ms 이하)이었다.
2. 대화 메시지 개수(→ 캔버스 다시 그리기 비용)와 다중 모니터 DPI 배율 차이도
   사용자에게 직접 확인해 배제했다.
3. `py-spy`(pip으로 설치해 사용)로 실제 실행 중인 프로세스를 직접 샘플링 — 사용자가
   실제로 창을 드래그하는 동안 인터프리터가 대부분(92~96%) `mainloop` 대기 상태였고,
   유일하게 드래그 구간에 집중적으로 나타난 파이썬 콜스택은 `dnd_handler.py`의
   `get_msg_proc`(파일 드래그앤드롭·트레이 아이콘 클릭 감지용 `WH_GETMESSAGE` 스레드
   훅)였다.
4. 확정을 위해 이 훅만 설치하지 않은 앱 사본을 나란히 띄워 사용자가 직접 비교 —
   훅이 없는 창은 가볍고, 있는 창은 무거움을 확인.

**원인**: `WH_GETMESSAGE` 훅이 스레드의 모든 윈도우 메시지를 가로채면, Windows가
평소 밀린 `WM_MOUSEMOVE`를 자동으로 병합(coalescing)해 가볍게 처리하던 것을 매번
개별적으로 파이썬 콜백까지 통과시켜야 하게 되어, 빠른 마우스 이동(=드래그) 중
누적 지연이 발생한다.

## 수정 (`dnd_handler.py`)

훅을 완전히 제거하면 파일 드래그앤드롭·트레이 클릭 감지 기능이 죽으므로, 대신
**창이 실제로 이동/크기조절되는 동안만 훅을 일시적으로 해제(`UnhookWindowsHookEx`)
했다가, 움직임이 멎으면(500ms 동안 추가 `<Configure>`가 없으면) 자동으로
재설치(`SetWindowsHookExW`)** 하도록 변경했다. `<Configure>`는 이동·크기조절
내내 계속 발생하므로, 매번 들어올 때마다 재설치 타이머를 뒤로 미루는 디바운스
방식이다(최초 250ms로 시도했으나 커서 속도가 느려지는 구간에서 훅이 잠깐
되살아나는 것을 py-spy로 확인해 500ms로 늘렸다).

## 검증

- `py-spy`로 실제 프로세스에 정확한 시간 동안(프로그램으로 커서를 직접 제어)
  드래그를 재현하며 재측정: 훅 관련 콜스택 비중이 눈에 띄게 감소.
- 기존 회귀 스위트 3종(`test_headless.py`, `test_gui_flow.py`, `smoke_gui.py`)
  재실행, 전부 통과.
- `python -m py_compile`로 문법 확인.

## 의도적으로 하지 않은 것 / 추가로 밝혀진 사실

- 이 수정을 적용한 뒤에도 사용자의 특정 PC에서는 여전히 무거웠다. 같은 코드가
  **다른 컴퓨터에서는 정상**이었고, Windows 기본 프로그램인 작업 관리자도 그 PC에서
  똑같이 무겁게 드래그되는 것으로 확인되어, 남은 증상은 이 코드베이스의 버그가
  아니라 **그 특정 PC의 그래픽 드라이버/합성(compositor) 환경 문제**로 결론지었다.
  이번에 고친 `WH_GETMESSAGE` 오버헤드는 그와 별개로 실재하는 버그였으므로 수정을
  유지한다.
