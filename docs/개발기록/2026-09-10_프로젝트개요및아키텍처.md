# 프로젝트 개요 — 목적·제약·아키텍처·초기 버그 이력·검증·한계·보안 리스크·로드맵 (2026-09-10)

이 문서는 프로젝트 초기(v1.3 무렵)에 작성된 참고 자료로, 이후 버전별 상세 변경 이력과는
별도로 "왜 이렇게 만들었는가", "무엇을 실측으로 확인했는가", "아직 남은 한계는 무엇인가"를
정리해둔 기준 문서다. 이후 개별 버전 변경 이력은 각자의 파일(`v2.0` 이후)을 참고.

## 1. 개발 목적과 제약

- **요구**: 서버 없이 사내에서 메시지를 주고받는 매신저. 상대 프로그램을 상시 켜둘 관리서버도 없음.
- **해법**: P2P(단대단) 방식. 자동 발견은 UDP 브로드캐스트, 실제 대화는 UDP 유니캐스트 직송.
- **환경 제약**:
  - 폐쇄망 — 외부 패키지 설치 불가 → **Python 표준 라이브러리만 사용** (tkinter, socket, json, threading).
  - 상시 구동 서버를 둘 수 없음 → 서버 모드를 아예 두지 않는 설계.

## 2. 아키텍처 (v1.3)

```
[프로세스 구조]
GUI (tkinter, 이벤트 펌프 80ms)
 └ Engine (네트워크 계층) ── 이벤트 큐로만 GUI와 통신
    ├ presence 스레드: 3초 간격 브로드캐스트(포트 50707) + 등록 IP 직송
    ├ recv 스레드: 패킷 수신 → presence / msg / ack 분기
    └ send worker: 전송 → ACK 대기(1.2초) → 미확인 시 3회 재전송 → 실패 보고
```

| 항목 | 내용 |
|---|---|
| 포트 | UDP 50707 (고정, `--port`로 변경 가능) |
| 패킷 | JSON(UTF-8): `presence`(자기소개) / `msg`(메시지) / `ack`(수신포고) |
| 발견 | 같은 세그먼트=브로드캐스트 · 다른 세그먼트=[IP 직접 추가] 등록 IP( `IP` 또는 `IP:포트`) |
| 신뢰성 | ACK 미수신 시 3회 재전송 → GUI에 빨강 실패 안내. 중복 표시 방지는 수신 측 최초 표시 기준 |
| 기록 | `logs\<IP>_<포트>.jsonl` — 이름이 아닌 주소 기준(이름 변경·착오에도 이력 보존) |
| 이름 | 기본값 Windows 계정명, 상단에서 언제든 변경(변경 즉시 presence 재전파) |
| GUI | 솔리드 네이비 테마(기존 내부 도구 디자인 체계), 좌: 동료 목록(상태/이름/IP, 읽지 않음 카운트) · 우: 채팅+입력 |
| 목록 정리 | 12초 무응답 동료는 목록에서 제외(등록 IP는 "대기"로 표시 유지) |

## 5. 현재 검증 망의 한계 (반드시 숙지)

실험실은 **단일 Windows VM 안의 루프백 가상랜**입니다. 이 때문에 다음은 검증 대신 "설계 의도"로만 존재하며 **실제 PC 2대+사내망에서 최초 확인이 필요**합니다:

1. **브로드캐스트 자동 발견 실섬 실패 — 루프백 미검증**: 루프백 실험실에는 브로드캐스트가 되돌아올 물리 세그먼트가 없어, 같은 세그먼트 자동 발견은 static(직접 IP) 경로로만 검증했습니다. 실제 LAN에서 첫 동작(서로 다른 PC에서 띄웠을 때 목록 자동 등장)은 **현장 1회 확인 필수**.
2. **다중 세그먼트(서브넷 분리) 상황**: 라우터가 브로드캐스트를 차단하는 정상 구조이므로, 분리 구역 간에는 반드시 [IP 직접 추가]가 필요합니다. 사내 세그먼트 구성(무선/인쇄/체류/VLAN 등)에 따라 "같은 층인데 안 보임"이 이로 인한 것이며 앱 결함이 아닙니다.
3. **다중 IP PC**: 여러 인터페이스(유선+무선+가상 어댑터)를 쓰면 브로드캐스트 경로에 따라 상대가 다른 IP로 발견할 수 있습니다. 현장에서 목적에 맞는 인터페이스 우선순위가 실측 필요합니다.
4. **성능/스팸 정책**: 3초 간격 브로드캐스트는 소량 트래픽이나, 관제 시스템이 작은 패킷 반복을 탐지하면 문의가 올 수 있습니다. 필요 시 주기를 늘리는 옵션(`--interval`)을 다음 버전에서 제공.
5. **장시간 리부트/서스펜드 회복**: 절전 복귀 후 소켓과 presence 주기 회복은 설계상 자동이나, 실 PC 절전·부팅 시나리오는 미실측.

## 6. 보안 프로그램·사내 정책 리스크 (반드시 숙지)

사내 PC에는 엔드포인트 보안 계열이 상주하며(사용자 실측: **MOCOMSYS Mpower NEOPCHook64.dll 인젝션, MNetDrive CBFS 가상 F:·G:·H:, AhnLab V3 v3amsi64, ubCUBE ubciox64** — 사용자 판정: 엑셀 지연 주범은 Mpower), 이 프로그램에 다음 영향이 가능합니다:

1. **미서명 파이썬 프로세스 감시 대상**: 보안 제품이 DLL을 인젝션해 소켓·프로세스 동작을 감시/지연할 수 있습니다. 엑셀에서 실측된 것과 같은 방식으로, UDP 소켓 생성·전송이 매끄럽게 안 될 가능성. **완화 패턴(엑셀 사례와 동일): C: 로컬 드라이브에서 소스 실행** — 네트워크 드라이브(D:·F:·G:·H:)에서 실행하면 보안 제품이 파일 I/O를 가로채 첫 실행이 몇 초 늦거나 감사 로그가 남을 수 있음.
2. **포트 정책**: UDP 50707 수신은 방화벽 허용이 필요하고, 관리팀 정책에 따라 앱별 차단 가능성이 있습니다. 방화벽 경고창에서 [액세스 허용]이 떴는데도 목록이 안 보이면 **관리팀에 UDP 50707(수신, 인바운드) 허용 문의**.
3. **DRM/서명 차단**: 폐쇄망 실측 데이터에 따르면 서명 없는 PyInstaller .exe는 DRM/HIPS가 파일 접근을 차단합니다. 따라서 **exe 배포는 하지 않는 것을 원칙**으로 하고, 파이썬 소스 + bat 런처 형태로 배포합니다 (내부 PKI 서명 자체는잘못 알려진 방식이 아닌 확인 가능한 대안이나, 사내 승인 절차가 필요).
4. **감사 로그**: 사내에서 미승인 통신 시도로 표시될 수 있습니다. 배포 전 관리팀(보안 담당)에게 목적·사용 범위·포트를 정식 통보해 두는 것이 안전합니다.
