# v6.10 대화 로그 저장소 암호화(secret.key 재사용) + 기존 평문 로그 자동 마이그레이션 (2026-09-13)

- **계기**: v6.9 결함 수정 작업 중 상용 메신저 대비 개선점을 분석해달라는 요청에서
  "로컬 저장소 암호화" 항목이 나왔다. 처음엔 워터마크·PIN 잠금과 함께 보류하기로
  했다가, 사용자가 "파일 암호화 하면 좋지"라며 진행을 확정. 키 관리 방식은
  ①`secret.key` 재사용(투명, 사용자 조작 없음) vs ②별도 4자리 PIN(더 강한 보호,
  매번 입력 필요) 중 사용자가 ①을 선택.
- **왜 `crypto_layer.encrypt()`/`decrypt()`를 그대로 못 쓰는가**: 네트워크 패킷용
  함수는 `MAX_CLOCK_SKEW`(2분) 시계 오차 검사와 재전송(replay) 공격 방어 캐시가
  있다. 저장된 로그는 "몇 달 뒤에도, 같은 줄을 몇 번이고 다시" 복호화할 수 있어야
  하는데, 이 두 안전장치가 정확히 그걸 막아버린다(오래된 레코드는 시계 오차 초과로,
  두 번째 읽기는 재전송 공격으로 오판해 복호화 실패). 그래서 `crypto_layer.py`에
  타임스탬프·재전송 캐시가 없는 별도 포맷 `encrypt_blob()`/`decrypt_blob()`을
  추가했다(매직 바이트도 `\x02`가 아닌 `\xb1`로 구분해 두 포맷이 섞이지 않게 함).
  nonce+HMAC 인증 자체는 기존 `_keystream`/`_xor_bytes` 헬퍼를 그대로 재사용.
- **라인 포맷**: 기존 `.jsonl`의 한 줄(JSON 한 개)을 `json.dumps().encode()` →
  `encrypt_blob()` → `base64.b64encode()` 순으로 변환해 여전히 텍스트 한 줄(개행
  구분)로 저장한다. 그래야 기존의 "한 줄씩 append", "파일 끝 8KB만 읽어 마지막
  레코드만 파싱"(`_read_last_record_from_file`) 같은 라인 지향 로직을 구조 변경 없이
  그대로 재사용할 수 있다. `engine.py`에 `_enc_log_line(rec)`/`_dec_log_line(line)`/
  `_dec_log_line_detailed(line)` 세 헬퍼를 추가해 모든 로그 읽기/쓰기 지점(총
  11곳: `load_history`, `_append_log`, `_append_log_file`, `_flush_read_ack`,
  `load_group_history`, `_append_group_log`, `_append_group_log_file`,
  `_merge_group_history`, `_flush_gread_ack`, `search_all_logs`,
  `_read_last_record_from_file`)을 이 헬퍼로 통일했다.
- **하위 호환 + 자동 마이그레이션**: `_dec_log_line_detailed()`는 먼저 base64+복호화를
  시도하고, 실패하면(평문 JSON은 애초에 base64 알파벳이 아니라 `validate=True`에서
  바로 걸러짐) 예전처럼 `json.loads()`로 평문 읽기를 시도한다 — 즉 마이그레이션
  여부와 무관하게 항상 정상적으로 읽힌다. 그 위에 `_migrate_plaintext_logs()`를
  얹어 `Engine.__init__` 마지막에 데몬 스레드로 실행: `data/logs/` 안의 모든
  `.jsonl` 파일을 훑어, 평문 줄이 하나라도 섞여 있으면 파일 전체를 복호화해 다시
  암호화한 뒤 `_atomic_write_text()`(v6.9에서 만든 원자적 쓰기)로 안전하게
  교체한다. 이미 여러 달 실사용 중인 대화 기록이 있어, 앱을 그냥 켜기만 해도
  자동으로 안전해지도록 설계했다(사용자가 버튼을 누르거나 기다릴 필요 없음).
- **검증**: 실제 `Engine`을 띄워 (1) 새로 쓴 로그 파일을 열어보면 원문이 전혀
  안 보이고 base64 텍스트뿐인지, (2) 그 상태에서 `load_history`/
  `get_last_history_record`(캐시 우회, 파일 끝 8KB tail 읽기 경로)/
  `search_all_logs`가 전부 정상적으로 원문을 복원하는지, (3) 구버전 평문 로그
  파일을 미리 만들어둔 채 Engine을 새로 띄우면 몇 초 안에 백그라운드에서 파일이
  암호화 형식으로 바뀌고 내용은 정확히 보존되는지, (4) 마이그레이션이 끝나기 전에
  읽어도(경쟁 상태) 평문 레코드가 정상적으로 로드되는지까지 8가지를 직접 확인했다.
  기존 회귀 스위트 3종도 재실행해 전부 통과 확인.
- **의도적으로 범위에서 뺀 것**: `settings.json`/`groups.json`/아바타/`.part`
  파일은 이번 작업 대상이 아니다 — 실제 대화 "내용"이 담기는 곳은 `data/logs/`
  뿐이라 거기에 집중했다. 워터마크(캡처 방지)와 PIN 잠금은 사용자 요청으로 이번
  범위에서 제외.
