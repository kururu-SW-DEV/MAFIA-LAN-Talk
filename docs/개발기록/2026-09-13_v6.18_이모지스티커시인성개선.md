# v6.18 — 이모지·스티커 시인성/여백 개선 (2026-09-13)

- **계기**: v6.17에서 만든 오리지널 스티커 28종 + 이모지 피커를 실제 앱에서 스크린샷으로
  확인한 사용자 피드백. "스티커나 이모지나 이렇게 몰려있고", "이모지의 경우 검은색이라
  시인성이 떨어져. 칼라로 바꿔줘", "스티커 중에 검은색 글씨를 가진 거는 시인성이 떨어져.
  흰색 테두리를 글자에 두는건 어떠니?" — 3가지를 한 번에 요청받아 순서대로 처리했다.

## (1) 이모지 검은색 단색 문제

- **원인**: `widgets.py`의 `EmojiPicker._switch_cat()`에서 이모지를 그리는 `tk.Label`에
  `fg=` 색을 전혀 지정하지 않아 Tk 기본 전경색(검정)으로 렌더링되고 있었다. 다크 테마
  배경(`C_CARD`)과 대비가 없어 특히 "제스처" 카테고리(손 모양 글리프가 많음)에서 거의
  안 보이는 수준이었다.
- **근본적인 한계**: Windows Tk는 GDI 텍스트 렌더링을 쓰기 때문에 Segoe UI Emoji의
  COLR/CPAL(컬러 폰트 글리프 테이블)을 읽지 못하고, 어떤 폰트를 지정해도 항상 단색
  아웃라인만 그린다. 즉 `tk.Label`/`Canvas.create_text`로는 진짜 이모지처럼 글리프마다
  다른 색이 섞인 렌더링이 원천적으로 불가능하다 — 이번 수정은 이 한계를 없애는 게 아니라
  그 안에서 최대한 알아보기 쉽게 타협한 것이다.
- **수정**: `EMOJI_CATEGORIES`의 각 카테고리 튜플에 색상을 추가해
  `(카테고리명, 이모지목록, 색상)` 3-튜플로 확장(기존 2-튜플 → 3-튜플이라 `self._cats`를
  쓰는 모든 곳 — 탭 버튼 생성, `_switch_cat`, "최근"/"스티커" 두 특수 탭 항목 — 동시에
  맞춰 고쳤다). 스마일리 `#FFC93C`(노랑), 제스처 `#F5B183`(살구), 하트 `#FF6B81`(핑크),
  동물 `#8BC34A`(연두), 음식 `#FFA65C`(주황), 활동/사물 `#5FD6C1`(민트) — 카테고리 성격에
  맞는 색을 배정해 카테고리 간 구분도 덤으로 좋아졌다. "최근" 탭은 기본 텍스트색(`C_TEXT`)
  유지.

## (2) 그리드 여백(몰려있음) 문제

- **원인**: 이모지 그리드(`_switch_cat`)는 `lbl.grid(row=r, column=c)`에 `padx`/`pady`가
  전혀 없었고, 스티커 그리드(`_render_stickers`)는 `padx=2, pady=2`로 너무 좁았다.
- **수정**: 이모지 그리드는 `padx=4, pady=4`로 늘려 항목 사이 여백을 확보했다.
  스티커 그리드는 1차로 `padx=6, pady=6`을 적용했으나, 실제 화면 재확인 결과 원 자체가
  56px 셀의 대부분(반지름 24)을 차지해 여전히 촘촘해 보인다는 피드백을 받아 2차로
  `padx=12, pady=12`로 다시 늘리고 원 반지름도 `cell/2-4`(24) → `cell/2-9`(19)로 줄여,
  칸 안쪽과 칸 사이 여백을 동시에 확보했다. (헤드리스 검증만으로는 "패딩 수치는 맞는데
  체감상 여전히 빽빽해 보인다"는 것까지는 잡히지 않아, 별도의 일반 `tk.Tk()` 창에 같은
  그리드를 그려 `PIL.ImageGrab`으로 실제 스크린샷을 찍어 확인하는 방식을 추가했다 — 이
  방식은 `tk.Toplevel`이 아니라 일반 루트 창이라 이 환경의 고질적인 Toplevel 행 문제를
  피해간다.)

## (3) 스티커 캡션 시인성(어두운 글자) 문제

- **원인**: `stickers.py`의 문구 스티커 14종은 캡션을 `_text(...)`로 단색만 그리고 있어,
  어두운 배경색 위에 어두운 글자색을 쓴 캡션(OK·NO·점심콜? 등 11종)은 대비가 부족했다.
- **수정**: Tkinter Canvas 텍스트에는 SVG 같은 `stroke` 속성이 없어서, 같은 텍스트를
  8방향으로 1px씩 오프셋을 줘 테두리색으로 먼저 그리고 그 위에 원래 색으로 다시 한 번
  그리는 `_text_stroke(c, cx, cy, s, x, y, txt, fill, stroke, size, bold)` 헬퍼를 새로
  만들었다. 14개 문구 스티커 캡션을 모두 `_text` → `_text_stroke`로 교체하면서, 어두운
  글자색 11종은 흰색(`#ffffff`) 테두리를, 이미 밝은 글자색을 쓰는 3종(저녁콜?·굿나잇·최고!)
  은 흰 테두리가 오히려 안 보이므로 각 스티커의 어두운 톤에 맞춘 진한 테두리색을 줬다.
- **부수적으로 발견한 버그**: 이 작업 중 "굿모닝"·"굿나잇"·"잠깐!" 캡션이 실제로는
  "꽿모니"·"꽿나잇"·"잠깜!"처럼 깨진 글자로 그려지고 있었다는 걸 발견했다. v6.17 초안에서
  이 세 캡션만 `\uXXXX` 유니코드 이스케이프로 손으로 타이핑했는데, 그 코드포인트 자체에
  오타가 있었던 것(예: "굿"의 정확한 코드포인트는 `0xAD7F`인데 다른 값을 썼음). `python -c
  "print([hex(ord(c)) for c in ch])"`로 정확한 코드포인트를 확인한 뒤, 이스케이프 대신
  리터럴 한글 문자를 직접 입력하는 방식으로 교체해 이 오류 유형 자체를 없앴다.

## (4) 그리드 자체가 여전히 왼쪽에 몰려 보이는 문제

- **원인**: 탭 바를 균등 분배하면서(아래 (5)) 탭 바가 요구하는 자연 너비(8개 탭 합산)가
  기존 캔버스 고정 너비(256px, `_CELL*_COLS`)보다 커져 팝업 전체 폭이 넓어졌는데(실측
  ~414px), 이모지/스티커 그리드를 담는 `inner` Frame은 `canvas.create_window(..., anchor="nw")`
  로 캔버스 왼쪽 위에 고정 배치되어 있어 캔버스가 넓어져도 내용물은 계속 왼쪽에만 붙어
  있고 오른쪽은 빈 공간으로 남았다. (3)에서 원 사이 간격을 넓힌 것과는 별개의, 더 상위
  레벨의 배치 문제였다.
- **수정**: `create_window` 앵커를 `"nw"` → `"n"`(상단 가운데)으로 바꾸고, 캔버스와
  `inner` 양쪽에 `<Configure>` 핸들러(`_reflow_inner`)를 걸어 캔버스 실제 폭이 바뀔
  때마다 `canvas.coords(inner_win, canvas_width // 2, 0)`으로 다시 가운데 정렬하도록
  했다. 스크롤 영역(`scrollregion`) 갱신도 같은 핸들러로 합쳤다.
- **검증**: 이 클래스는 `tk.Toplevel`이라 실제로 `deiconify()`하면 이 세션이 멈추기
  때문에, `EmojiPicker.__init__` 내부 구조(탭 바 `grid`+균등 weight, 캔버스/스크롤바/
  `inner` 배치, `_reflow_inner`)를 **일반 `tk.Tk()` 루트 창**에 그대로 재현해 실제로
  화면에 그린 뒤 `PIL.ImageGrab`으로 스크린샷을 찍어 확인했다(일반 루트 창은 이 환경에서
  멈추지 않음이 이전에도 확인된 방식). 처음 시도에서는 Windows 고DPI 스케일링 때문에
  `winfo_*`가 반환하는 논리 픽셀 좌표와 `ImageGrab`이 쓰는 물리 픽셀 좌표가 어긋나
  캡처 영역이 실제 창보다 좁게 잘려 옆의 다른 창(데스크톱) 내용이 비쳐 보이는 문제가
  있었는데, 스크립트 시작 시 `ctypes.windll.shcore.SetProcessDpiAwareness(1)`로 프로세스를
  DPI 인식 상태로 만들어 해결했다(이 문제는 실제 코드 버그가 아니라 검증 스크립트 쪽의
  캡처 좌표계 문제였다). 최종 스크린샷에서 탭 8개가 폭 전체에 고르게 펼쳐지고, 스티커
  그리드도 캔버스 왼쪽 끝에 붙지 않고 가운데로 이동한 것을 확인했다. 수치로도
  `canvas.winfo_width()=414`, `inner`의 중심 좌표가 정확히 그 절반(207)에 위치함을
  별도로 확인.

## (5) 카테고리 탭 바 몰림 문제

- **원인**: "이모티콘 과 이모지가 이 한쪽에 몰려 있잖아" 라는 후속 피드백 — 위 3가지를 고친
  뒤, 피커 맨 위 카테고리 탭 바("최근"·"스티커"·스마일리·제스처·하트·동물·음식·활동/사물
  8개)를 다시 보니 각 탭이 `pack(side="left")`로만 배치되어 있어 탭 문구 길이만큼만
  공간을 차지하고 나머지는 왼쪽으로 쏠려 뭉쳐 있었다(오른쪽 여백은 텅 비어 있음).
- **수정**: 탭 바를 `pack` 대신 `grid`로 바꾸고, 탭 개수만큼 `columnconfigure(..., weight=1)`
  을 줘서 각 탭이 동일한 비율로 폭 전체에 균등하게 펼쳐지도록(`sticky="ew"`, 텍스트는
  `anchor="center"`) 했다. 이제 8개 탭이 피커 폭 전체에 고르게 분산되어 한쪽으로 몰리지
  않는다.

## (6) 팝업 위치가 메신저 창 아래로 벗어나는 문제

- **계기**: "선택 창의 위치가 조절도 안되는데, 조절이 안되어도 매신저창의 최하단에
  맞추면 문제가 없는데, 매신저의 최하단보다도 더 밑에 있어 불편해." — 팝업을 드래그로
  옮기는 기능까지는 필요 없지만, 적어도 메신저 본창의 아래 경계를 넘어가면 안 된다는
  요청.
- **원인**: `app.py`의 `_toggle_emoji_picker()`가 이모지 버튼 위치에서 고정으로 `-220`만큼
  위로 띄워 여는데(`self._emoji_picker.show(x, y - 220)`), 이 오프셋은 피커의 대략적인
  예상 높이를 가정한 매직 넘버라서 실제 높이가 이보다 크거나 이모지 버튼이 창 아래쪽에
  가까울 때는 팝업의 아래쪽 끝이 메신저 본창의 맨 아래 경계를 넘어가 버렸다.
- **수정**: `widgets.py`의 `EmojiPicker.show(x, y)`에서, 팝업을 띄우기 직전에
  `update_idletasks()`로 실제 필요한 높이(`winfo_reqheight()`)를 구하고, 소유자 창
  (`self._owner_root`, 즉 메신저 본창)의 아래 경계(`winfo_rooty() + winfo_height()`)를
  계산해 `y + 높이`가 그 경계를 넘으면 `y`를 `본창_아래경계 - 높이`로 눌러 내리도록
  (clamp) 했다. 호출부(`app.py`)는 그대로 두고 위젯 자체가 항상 스스로 범위를 벗어나지
  않도록 방어하는 구조라, 다른 화면 크기나 이모지 버튼 위치에서도 동일하게 안전하다.
- **검증**: `EmojiPicker`를 생성한 뒤 `deiconify`/`lift`만 무해한 no-op으로 바꿔치기해서
  (실제 창을 띄우지 않고) `show()`를 호출 — (1) 메신저 창 아래 경계를 한참 넘는 `y`를
  요청하면 실제로 `본창_아래경계 - 팝업높이`로 눌러 내려지는지, (2) 이미 경계 안쪽인
  안전한 `y`를 요청하면 값이 그대로 유지되는지(불필요하게 건드리지 않는지) 둘 다 확인 —
  통과.

## 의도적으로 하지 않은 것

- Tk의 컬러 이모지 렌더링 한계를 우회하는 더 복잡한 방법(예: 컬러 이모지를 PNG로
  사전 렌더링해 `PhotoImage`로 붙이는 방식)은 이번에는 적용하지 않았다 — 150개 이상의
  이모지 전체를 이미지로 미리 만들어 배포에 포함시키는 건 "외부 자산 없이 코드로 직접
  그린다"는 이 프로젝트의 기존 원칙 및 스티커 구현 방향과 배치되고, 범위도 커서 별도
  논의가 필요하다고 판단했다.
