# v6.7 사이드바 스크롤 완전 수정, 알림 클릭 이동, 이름/검색창 텍스트 정제 확대 (2026-09-13)

- **"왼쪽 대화 목록이 많으면 스크롤이 안 된다" — 실제로는 서로 다른 버그 두 개가 겹쳐 있었다**:
  1) **스크롤바 자체가 안 뜨는 버그**: `_plist_cfg()`가 "스크롤이 필요한지"를 `scrollregion`을
     최신 내용 크기로 갱신하기 **전에** 먼저 판정하고 있었다. `_refresh_list()`로 행이 한꺼번에
     왕창 늘어나는 상황에서는 판정이 항상 한 박자 낡은 정보를 봐서, 스크롤바가 끝내 안 뜨는
     경우가 있었다. `scrollregion` 갱신 → 판정 순서로 바로잡았다.
  2) **순서를 고쳐도 여전히 안 뜨는 Tk 자체의 함정**: `expand=True, fill="both"`로 이미 폭
     전체를 차지한 위젯(목록 캔버스) 옆에 나중에 형제 위젯(스크롤바)을 `pack()`해도, Tk가
     기존 위젯의 자리를 안 비켜줘서 스크롤바가 폭 1px로 찌그러진 채(`winfo_ismapped()==False`)
     화면에 안 뜨는 것을 최소 재현 스크립트로 직접 확인했다. 스크롤바를 pack한 **직후 목록
     캔버스를 pack_forget → 재pack**해서 Tk가 폭 배분을 새로 계산하도록 강제해 해결(반대
     방향, 즉 스크롤바를 숨길 때는 재pack 없이도 캔버스가 자동으로 폭을 되찾는 것도 확인).
  3) **스크롤바가 떠도 마우스 휠이 안 먹는 문제**: 목록의 각 행(이름·미리보기 라벨 등)은
     캔버스 위에 그린 게 아니라 진짜 자식 위젯이라, 캔버스에만 `<MouseWheel>`을 걸면 행 위에
     마우스가 있을 때 이벤트가 그 자식 위젯에서 끝나버려 휠이 안 먹는다(채팅 캔버스는 전부
     `create_text`/`create_image`라 이 문제가 원래 없었음). 목록 영역(`lw`)에 마우스가
     들어오고 나갈 때만 `bind_all("<MouseWheel>", ...)`을 걸었다 풀었다 하는 방식으로 교체해,
     자식이 몇 겹이든 항상 스크롤되게 했다.
  - 덤으로 스크롤바 디자인도 기본 흰색 `ttk.Scrollbar`에서 채팅창에 이미 있던
    `MinimalScrollbar`(카카오톡풍)로 통일했다("스크롤 디자인이 이게 뭐야" 피드백 반영).
  - 검증: 가짜 대화 30~40개를 등록해 실제로 넘치는 상황을 만든 뒤, 스크롤바 표시 여부·자식
    라벨 위 휠 스크롤·마우스가 벗어나면 휠이 다시 안 먹는지까지 전부 스크린샷·스크립트로 확인.
- **알림 동작 두 가지 수정**:
  1) **포커스 중에도 알림이 뜨던 버그**: `_notify_if_needed()`의 억제 조건이
     `focused and self.current == key`였다 — 창이 포커스돼 있어도 "지금 보는 대화방이 아니면"
     알림이 떴다. 조건을 `focused`만으로 단순화해서, 창이 활성 상태면 어느 대화방을 보고
     있든 무조건 억제하고 최소화·비활성 상태일 때만 뜨도록 고쳤다.
  2) **알림 클릭 시 대화방 이동 기능 신설**: `winapi.Notifier`가 트레이 아이콘 등록 시
     `NIF_MESSAGE` 플래그와 콜백 메시지(`uCallbackMessage=WM_TRAYICON`)를 같이 등록하도록
     확장하고, `on_click` 콜백을 받도록 생성자를 변경했다. 이미 드래그 앤 드롭에 쓰던
     `WH_GETMESSAGE` 스레드 훅에 이 클릭 메시지 감지를 추가했는데, **훅 콜백 안에서 직접
     Tkinter API를 부르면 Tcl이 GIL 없이 호출돼 인터프리터가 패닉나는 것으로 이미 드래그 앤
     드롭 때 확인된 바 있어**, 여기서도 순수 파이썬 불리언 플래그(`_notify_click_pending`)만
     세워두고 기존 80ms 메인 루프(`_pump`)에서 안전하게 처리하도록 했다. 클릭하면 창을 복원
     (`deiconify`→`state("normal")`→`lift`→`focus_force`)하고 알림이 어느 대화방
     소식이었는지(`_last_notify_key`) 기억해뒀다가 그 대화방으로 이동한다.
  - 검증: 실제 `Notifier`를 만들어 아이콘 등록이 여전히 성공하는지, `on_click` 연결이 되는지
    스크립트로 확인. 특히 클릭 자체는 — 사람이 화면 구석의 토스트를 마우스로 정확히 누르는
    건 자동화 환경에서 재현이 어려워(토스트가 몇 초 안에 사라짐), 실제 클릭이 발생했을 때
    Windows가 보내는 것과 완전히 동일한 시스템 메시지(`WM_TRAYICON` + `NIN_BALLOONUSERCLICK`)를
    `PostMessage`로 실제 실행 중인 창의 진짜 핸들에 직접 주입해서, 그 메시지를 받았을 때
    실행되는 코드 경로 전체(훅→큐→메인루프→창 복원/이동)가 실제 프로세스에서 정상 동작하는지
    끝까지 확인했다(마우스 클릭 동작 자체가 아니라 그 클릭이 발생시키는 실제 코드 경로를
    검증한 것 — `IsIconic` False 전환과 대상 대화방으로의 실제 이동을 스크린샷으로 확인).
- **이름 관련 텍스트 정제(살균) 범위 확대 — "아직도 문제 있다"는 피드백을 받고 두 단계로 확장**:
  1) 1차: 채팅 메시지 본문에만 적용되던 이형 문자 선택자(U+FE0F) 제거 처리가 **상대방 이름**
     에는 빠져 있던 것을 발견. `Engine._upsert_peer()`(모든 이름 갱신 경로가 공통으로 거치는
     지점)와 `_upsert_group()`, `set_name()`에 `sanitize_chat_text()`를 추가해 presence·
     group_invite·group_msg로 들어오는 이름과 내 이름 변경을 한 번에 막았다. `app.py`의
     `_on_mention_select()`(멘션 자동완성 삽입)에도 방어적으로 한 번 더 살균을 추가했다.
  2) 사용자가 "타이핑 방식으로 검증해봐, 붙여넣기로는 재현 안 돼"라고 정확히 원인 방향을
     짚어줘서 재조사한 결과, 채팅 입력창의 실시간 정제(`_entry_resize`)가 **`<KeyRelease>`
     (물리적 키 입력)에만** 반응하고 있었던 게 진짜 원인이었다. Windows 이모지 패널(Win+.)이나
     일부 IME 완성 결과는 실제 키 이벤트 없이 텍스트가 바로 꽂히는 방식이라 이 실시간 정제를
     그냥 통과했다 — 반면 붙여넣기는 `<<Paste>>`라는 별도 가상 이벤트로 이미 막혀 있어서
     "타이핑은 재현되고 붙여넣기는 안 되는" 정확한 현상이 나타난 것. `<KeyRelease>`를 Text
     위젯 내용이 "어떻게" 바뀌든 다 잡아내는 **`<<Modified>>`** 가상 이벤트로 교체해 원천
     차단했다(재귀 호출로 두 번 도는 구조지만 살균이 멱등이라 안전하게 종료됨).
  3) 이어서 "다른 입력창도 검토해봐, 검색창 같은 거"라는 요청에 전수 조사: `tk.Entry`는
     `<<Modified>>`가 없지만, `textvariable`(StringVar)의 `trace_add("write", ...)`가 입력
     방식과 무관하게 내용이 바뀌는 모든 경우에 걸리는 것을 이용해 **사이드바 검색창**과
     **대화방 내 검색바(ChatSearchBar)** 양쪽에 동일한 실시간 정제를 추가했다. 또한
     `set_alias()`·`create_group()`·`rename_group()`(이름 변경/그룹 생성/그룹 이름 변경
     다이얼로그의 최종 저장 지점)에도 애초에 살균이 전혀 없었던 것을 발견해 추가했다 — 이
     값들은 한 번 저장되면 사이드바·채팅 헤더 등에 계속 재노출되므로 순간적인 타이핑 글리치
     보다 파급力이 크다고 판단해 우선 처리했다. IP 입력칸들과 모달 다이얼로그 자체의 입력창
     실시간 정제는 비용 대비 효과가 낮다고 보고 의도적으로 남겨뒀다(값 자체는 저장 시점에
     이미 정제되므로 지속되는 문제는 아님).
  - 검증: 각 단계마다 "이형 문자 선택자가 섞인 이름"을 실제로 만들어 저장/삽입 시점에
    제거되는지 스크립트로 확인했고, 특히 2)번은 `_entry_resize()`를 수동으로 부르지 않고
    `.insert()`만으로 텍스트를 넣은 뒤 Tk 이벤트 루프가 스스로 정리하는지까지 검증해 실제
    버그 재현 조건과 정확히 같은 방식으로 확인했다.
