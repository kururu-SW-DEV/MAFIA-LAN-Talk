# v6.11 자동 폭파(Self-Destruct) 타이머 메시지 — 1:1 전용, 읽은 시점부터 카운트다운 (2026-09-13)

- **계기**: 상용 메신저 비교 분석에서 나온 3개 보안 보강 항목(자동 폭파/로컬 저장소
  암호화/캡처 방지 워터마크) 중 워터마크는 제외, 자동 폭파는 처음부터 진행 확정,
  로컬 저장소 암호화는 v6.10에서 먼저 끝냈고 이제 자동 폭파 차례.
- **"읽은 시점"을 어떻게 아는가**: 이 앱엔 원래 읽음 확인(`read_ack`/`gread_ack`)
  흐름이 이미 있었다(v6.9에서 배치 처리로 최적화한 바로 그 코드). 잘 보면 "내가 받은
  메시지를 읽었다"는 시점은 이미 정확히 특정돼 있다 — app.py의 `_select()`(대화방을
  염) 또는 `_on_msg()`(대화방이 열려 있는 채로 새 메시지가 옴)에서 `send_read_ack()`를
  부르는 바로 그 순간이다. 그래서 새 이벤트나 새 트리거를 만들 필요 없이,
  `Engine.send_read_ack()` 안에 `_queue_burn_start()` 호출 한 줄만 얹었다. 마찬가지로
  "상대가 내 메시지를 읽었다"는 이미 들어오는 `read_ack` 패킷 자체이므로, 그걸 처리하는
  `_flush_read_ack()` 안에서 `unread` 플래그를 내리는 동시에 `burn_sec`이 있으면
  `burn_deadline = now + burn_sec`을 같이 세팅하도록 확장했다. 즉 **발신자·수신자 양쪽이
  각자 자기 로그에서, 이미 있던 두 개의 서로 다른 "읽음" 신호를 트리거로 삼아 독립적으로
  카운트다운을 시작**한다 — 새로운 프로토콜 조율이 거의 필요 없었다.
- **삭제 예약 배치**: read_ack와 똑같은 이유(여러 개가 한꺼번에 몰릴 수 있음)로
  "내가 받은 메시지를 읽었다"는 신호도 `_queue_burn_start`/`_flush_burn_start`로
  300ms 배치 처리한다(구조가 `_mark_read_in_log`/`_flush_read_ack`와 거의 동일 —
  대상 필드가 `unread`→`burn_deadline`, 방향이 `dir=="out"`→`dir=="in"`인 것만 다르다).
- **실제 삭제(만료 스윕)**: `PRESENCE_INTERVAL`(3초)마다 도는 기존 `_prune()`에
  `_sweep_burns()`를 얹었다. 대부분의 대화방은 자동 폭파를 안 쓰므로 매번 모든 로그
  파일을 훑는 대신, `burn_deadline`이 세팅된 적 있는 방만 `_burn_candidates` 집합에
  등록해두고 그 방들만 확인한다 — `now >= burn_deadline`인 레코드는 파일에서 완전히
  제거하고(원자적 쓰기로 재작성) `{"ev": "burned", "key": ...}` 이벤트를 쏴서 그 방이
  현재 화면에 떠 있으면 즉시 새로고침되게 했다. 더 이상 대기 중인 레코드가 없는 방은
  후보 집합에서 빠져 이후엔 스캔 대상에서 제외된다.
- **재시작 내구성**: `burn_deadline`은 로그 레코드 자체에 저장되므로(디스크에 영구
  기록), 타이머가 끝나기 전에 프로그램을 껐다 켜도 사라지지 않는다. v6.10에서 만든
  마이그레이션 스캔(`_migrate_one_log_file`, 앱 시작 시 1회, 모든 로그 파일을 어차피
  한 번씩 훑음)에 편승해서, 그 김에 `burn_deadline`이 있는 레코드를 발견하면
  `_burn_candidates`에 등록하도록 했다 — 별도의 전체 스캔을 추가하지 않고 기존 패스에
  끼워 넣은 것. 이미 만료됐어야 할 메시지가 있었다면 재시작 후 첫 `_prune()` 주기
  (최대 3초 이내)에 곧바로 정리된다.
- **UI**: 입력 바에 `⏱` 버튼을 새로 추가(첨부 버튼과 입력창 사이). 누르면
  기존 `_popup_menu()`를 재사용한 팝업으로 [끄기/30초/5분/1시간]을 고른다. 선택한
  값은 `App._burn_mode[key]`에 대화방별로 저장되며(카톡 "1:1 대화 자동 삭제"처럼
  꺼질 때까지 유지되는 방식), 켜져 있는 동안은 버튼 배경색이 강조색(`C_ME`)으로
  바뀐다. `PillButton`은 진짜 `tk.Button`이 아니라 Canvas에 직접 그리는 위젯이라
  `config(bg=...)`로는 색이 안 바뀐다는 걸 확인하고, 내부 속성(`bg_color`/
  `hover_color`)을 직접 바꾼 뒤 `_draw()`를 다시 호출하는 방식으로 처리했다.
  말풍선에는 타임스탬프 라벨 옆에 `🔥{기간}`(예: `🔥30초`)을 붙여 어떤 메시지가
  자동 삭제 대상인지 보이게 했다.
- **범위를 의도적으로 좁힌 부분**: (1) 그룹 대화는 지원하지 않는다 — 멤버마다
  "읽음" 시점이 다 달라서 "누가 읽었을 때부터 카운트다운?"이 모호해지고, 기존
  그룹 읽음 확인(`readers` 배열, 다인 대상)과 설계가 안 맞는다. (2) 파일/사진
  전송에는 적용하지 않는다 — 텍스트 메시지(`send_message`)에만 `burn_sec`을
  추가했고 `send_file` 경로는 건드리지 않았다.
- **알려진 한계(문서에도 명시)**: 상대가 삭제되기 전에 화면을 캡처하거나 텍스트를
  복사해두면 당연히 막을 수 없다(텔레그램 비밀대화도 동일한 한계). "완전히 복구
  불가능한 삭제"가 아니라 "평소 UI와 로그 파일에서 흔적을 없애는" 수준이며, 이는
  v6.10에서 로컬 저장소 암호화를 붙였어도 파일 자체를 삭제하는 것이지 디스크
  섹터를 안전 삭제(wipe)하는 것은 아니라는 한계와 같은 결의 제약이다.
- **검증**: 실제 Engine 두 개(A→B)로 종단간 테스트 — (1) `burn_sec`이 패킷/수신
  이벤트에 그대로 실림, (2) B가 읽으면(`send_read_ack` 호출) B 자신의 로그에
  `burn_deadline`이 기록됨, (3) 그 read_ack가 A에 도착하면 A 자신의 로그에도
  `burn_deadline`이 기록됨, (4) 실제로 몇 분/몇 시간을 기다리는 대신 `burn_deadline`을
  과거 시각으로 만들어(=만료 상황을 그대로 재현) `_sweep_burns()`를 호출하면 양쪽
  로그에서 정말로 레코드가 사라지고 `"burned"` 이벤트가 양쪽에서 발생하며 후보
  집합에서도 정리되는지 — 총 10개 항목 확인. 별도로 실제 `App` GUI 배선도 검증:
  대화 선택 시 버튼 활성/비활성(그룹은 비활성), 타이머 on/off에 따른 버튼 색 전환,
  대화방마다 독립적으로 상태가 유지되는지, `_send()`가 armed된 `burn_sec`을
  `engine.send_message()`와 화면 표시용 레코드 양쪽에 정확히 전달하는지까지 10개
  항목 확인. 기존 회귀 스위트 3종도 재실행해 전부 통과.
