# v6.8 경쟁 프로그램 비교 분석 후 3대 기능 도입 (친구 카테고리·다중 발송·파일 이어받기) (2026-09-13)

- **계기**: 사용자가 오픈소스 "LAN Messenger"(lanmessenger.github.io, Qt 기반)를 우리 앱과
  비교 분석해달라고 요청. 랜딩페이지·GitHub README·이슈 트래커까지 훑어본 결과, 문서 자체는
  얕았지만(빌드 가이드 위주) 이슈에서 실사용자 요구가 드러났다(예: "최신 버전에서 이미지 전송·
  테마가 왜 빠졌냐"는 불만 — 오히려 그쪽이 퇴보한 지점도 확인). 분석 후 우선순위 5개를 제안했고
  ("1번부터 순서대로 작업해봐" 지시에 따라) 1→3→2 순서로 구현, 4(라이트 테마)·5(알림음)는
  사용자가 보류 결정.
- **1) 친구 카테고리(폴더) 분류 (`engine.py`, `app.py`)**:
  - `Engine.contact_categories`(`"dm:ip:port" -> 카테고리명`, `settings.json`에 영속화)와
    `get_category`/`set_category`/`list_categories()` 추가. 별칭(`aliases`)과 완전히 동일한
    저장 패턴(`_load_categories`/`_save_categories`)을 재사용해 일관성 유지.
  - `_refresh_list()`의 [친구] 탭 분기에서 항목마다 `category = get_category(key) or "미분류"`를
    붙이고, 정렬 키를 `(카테고리순서, 온라인여부, 이름)`으로 확장. 카테고리 정렬은 "미분류"를
    항상 맨 뒤로 보내고 나머지는 가나다순.
  - 행 패킹 루프에 카테고리 헤더(`"카테고리명 (N)"`)를 매 새로고침마다 destroy 후 재생성해서
    끼워 넣음(행 자체는 기존처럼 diff 갱신 유지, 헤더만 검색결과 헤더와 같은 방식으로 가볍게
    다시 그림).
  - 우클릭 메뉴에 [📁 카테고리 지정] 추가 — 기존 카테고리 중 고르거나 `_prompt_text`로 새로
    만들거나 "미분류로 이동" 가능. 팝업 메뉴를 같은 클릭에서 연달아 두 번 여는 구조라, 앞 팝업의
    바깥클릭 감지 `bind_all`이 뒷 팝업을 즉시 닫아버리는 걸 막기 위해 `root.after(1, ...)`로
    한 틱 미뤄서 열었다(팝업 메뉴 구현 자체의 알려진 특성 — v4.2 기록 참고).
  - 검증: 실제 대화 상대 5명(카테고리 2개 + 미분류 2명 섞어서)을 등록해 스크린샷으로 그룹핑·
    정렬이 정확한지 확인.
- **2) 여러 명에게 한 번에 보내기 (`app.py`, `_broadcast_dialog`)**:
  - 그룹을 생성하지 않고, 체크박스로 고른 여러 명에게 `engine.send_message()`를 한 명씩 개별
    호출하는 방식 — 완전히 독립된 1:1 메시지 N개다(로스터·이력 공유 없음, group_msg 프로토콜과
    무관).
  - 기존 `_build_picker_list()`(그룹 생성·멤버 초대에 이미 쓰던 체크박스 목록 위젯)를 그대로
    재사용. 메시지 입력은 여러 줄이 자연스러워 `tk.Text`를 새로 두고, 채팅 입력창과 동일한
    `<<Modified>>` 기반 실시간 정제를 붙였다.
  - 검증: 실제 엔진 3개(A/B/C)로 A가 B·C 둘 다 선택해 보낸 뒤 — B·C 둘 다 수신하는지, 이
    과정에서 `engine.groups` 개수가 그대로인지(그룹이 생성 안 됐는지)까지 확인. 처음엔 위젯
    트리를 순회하며 클릭 이벤트를 흉내내는 방식으로 테스트했다가 dead-lock성 행(다이얼로그
    `grab_set` 자체는 문제 없었지만 클릭 시뮬레이션이 의도대로 안 먹어 스크립트가 멈춤)을
    겪어서, `_build_picker_list`를 임시로 몽키패치해 반환값(BooleanVar들)을 직접 캡처하는
    방식으로 바꿔 안정적으로 검증했다.
- **3) 파일 전송 이어받기(resume) — 가장 손이 많이 간 항목 (`engine.py`)**:
  - 기존 구조는 수신 측이 조각을 전부 메모리(`tr["chunks"]` dict)에 모았다가 마지막에 한 번에
    디스크로 썼다. 중간에 끊기면 통째로 버려지고, 재시도 시 처음부터 다시 받아야 했다.
  - **디스크 스트리밍 구조로 전면 개편**: 수신 조각이 도착하는 즉시 `data/partial/<해시>.part`
    파일에 순서대로 append하고, 완료되면 그 파일을 최종 위치로 `move`(더 이상 메모리에 전체를
    들고 있지 않아 메모리 사용량도 개선됨).
  - **재개 판정 프로토콜 추가**: `file_offer`를 받으면 `(대상·발신자·파일명·크기)`로 만든
    `resume_key`로 기존 `.part` 파일이 있는지 확인하고, 있으면 `file_offer_ack`(신규 패킷
    타입)에 `resume_from`을 실어 되돌려준다. 발신 측(`_file_send_worker`)은 오퍼를 보낸 뒤
    최대 2초간 이 응답을 기다렸다가, 구버전 상대이거나 응답이 없으면 기존과 동일하게 0부터
    보낸다(하위 호환 안전한 기본값). 응답이 있으면 `f.seek(resume_from * FILE_CHUNK_SIZE)`로
    이미 전달된 조각은 건너뛰고 나머지만 보낸다.
  - **영속 인덱스**: `data/partial/index.json`에 `resume_key -> {part 파일명, next_seq, total,
    ts}`를 저장해 **앱을 껐다 켜도** 이어받기가 유지되도록 했다. 시작 시 인덱스에는 있는데 실제
    `.part` 파일이 없는 고아 항목은 자동 정리하고, `_prune()`에 일주일 넘게 진행이 없는 `.part`
    파일을 지우는 장기 정리도 추가했다.
  - **실측으로 발견한 버그**: 디스크 I/O를 줄이려고 인덱스의 `next_seq`를 8조각에 한 번만
    저장했는데(`should_persist = done or next_seq % 8 == 0`), 정확히 8의 배수가 아닌 지점에서
    끊기면 "인덱스에 기록된 진행 상황"과 "실제 .part 파일 크기"가 어긋나게 되고, 재개 시 이
    불일치를 안전장치가 "파일이 깨졌다"고 오판해 매번 처음부터 다시 받아버렸다(재현: 500KB
    파일을 8조각 이전에 끊었을 때는 증상이 안 보였지만, 1MB 파일을 12조각째에 끊자 재현됨).
    수정: 재개 지점을 인덱스의 `next_seq`가 아니라 **`.part` 파일의 실제 바이트 크기에서
    역산**(`actual_size // FILE_CHUNK_SIZE`)하도록 바꿔, 인덱스 저장 주기와 무관하게 항상
    정확한 지점부터 재개하도록 고쳤다. 인덱스의 `next_seq`는 이제 참고용일 뿐, 정확성에는
    관여하지 않는다.
  - 검증: 1MB 파일(32조각)을 실제 두 엔진 사이에 전송하면서 12조각을 받은 시점에 수신 측을
    강제 종료 → 같은 datadir로 재기동(앱 재시작 재현) → 재전송 시 몇 조각이 실제로 다시
    전송되는지 `crypto_layer.encrypt`를 가로채 세어봄(32조각 중 19조각만 재전송 확인) →
    최종 수신 파일과 원본의 SHA256 해시가 완전히 일치하는지 확인. 기존 파일 전송 회귀
    테스트(0바이트 파일, 파일명 충돌 넘버링, 20MB 초과 거부, 그룹 팬아웃)도 전부 그대로 통과.
- 검증(공통): 매 기능마다 `python -m py_compile` + `test_headless.py`/`smoke_gui.py`/
  `test_gui_flow.py` 3종 무인 테스트 재실행, 전부 통과.
